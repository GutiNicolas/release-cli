# T-08: `sign` connector: cosign signature and SLSA provenance

- **Roadmap:** ../ROADMAP.md · **Phase:** 3 · **Repo:** release-cli · **Base branch:** release/go-apps-p3 (PR targets it, not main) · **Branch:** feature/sign
- **Depends on:** phase 2 merged · **Model:** sonnet · **Review tier:** read

## Goal
Anyone can check that a release's archives come from the maintainer and from the tagged commit, using a public key
the app publishes, without a hosted CI. It works the same on a laptop and in a local CI run.

## Scope
- Files: new `release_cli/sign.py` (built-in, entry point `sign`, declares `dry_run: safe`), `github_release.py`
  (uploads the new manifest entries), README section (how to verify, with the `cosign verify-blob` and
  `cosign verify-blob-attestation` commands), the go fixture.
- Runs after `go-build`: signs `checksums.txt` (`cosign sign-blob --key`, bundle `checksums.txt.sig`), writes an
  in-toto statement with a SLSA provenance predicate (subjects: every archive and its sha256; builder: release-cli
  and its version; source: repo, tag, commit; build flags from `[connectors.go-build]`) and signs it
  (`cosign attest-blob --key`, `<binary>_<version>.intoto.jsonl`), copies the public key as `cosign.pub`, and adds
  the three to the manifest.
- Keys: private key from secret `cosign-key` (PEM content), password from secret `cosign-password`, both through
  `release secret` (`RELEASE_SECRET_*` in a local CI). Written to a 0600 temp file only while cosign runs, then
  deleted. Public key path in config: `[connectors.sign] public_key = "cosign.pub"` (committed in the app repo).
  No transparency-log upload by default (`tlog = false`), so nothing about the maintainer is published.
- Dry-run: signs with a throwaway key generated in the temp dir, so the whole chain is checked without the real key.
- First step: confirm with cosign's docs that `attest-blob` / `verify-blob-attestation` with a key and no tlog work
  as above, and that npm provenance and GitHub attestations cannot be produced outside a hosted CI; record it in Result.
- Out of scope: CI-identity provenance (T-10).

## Contract
Roadmap → Decisions (provenance), Contracts (Layout, order, secrets). Result: `{"signed": [names], "public_key",
"tlog": false}`. Missing `cosign` → failed with the install hint; missing secret → failed with the

## Result (filled by the worker)

All criteria met (with one command-line deviation, below); PR against `release/go-apps-p3`.

**First step (cosign 3.1.4, run locally, no network needed after install):** `sign-blob` / `attest-blob --key` plus `verify-blob` / `verify-blob-attestation --key` work with no transparency log, and the key files are never uploaded. Two facts the spec did not know: (1) cosign 3 uploads every signature to the public Rekor log **by default**, even with `--key`, and rejects `--tlog-upload=false`; the way to say "no log" is `--signing-config` with a config that names no services (`{"mediaType": "...signingconfig.v0.2+json", "rekorTlogConfig": {}, "tsaConfig": {}}`, what `cosign signing-config create` prints), which `sign` writes to its temp dir; (2) verifying such a bundle needs `--insecure-ignore-tlog` (the signature and key are still checked). npm provenance and GitHub attestations need a hosted CI's OIDC identity token (Fulcio certificate / Actions token); a laptop or local CI has none, so they cannot be produced there (cosign and GitHub docs; consistent with the roadmap's phase 5). I did not re-test that against GitHub itself.

**Decisions and additions beyond the Contracts**
- SLSA provenance **v1** (`slsaprovenance1`), not the `--type slsaprovenance` of the criterion: in cosign that name is the deprecated v0.2 predicate, and a v1 statement fails it ("invalid predicate type"). Change the constant `PREDICATE_TYPE` (and `--type`) if v0.2 is wanted.
- The Result is `{"signed", "public_key", "tlog": false}` plus `"artifacts"`: the three manifest-style entries (`kind` `signature|provenance|publickey`). `signed` lists what was signed (`checksums.txt` and every archive). `github-release` reads `prior["sign"].result.artifacts` (only when sign is ok) because go-build's own manifest in `prior` cannot change; `manifest.json` on disk also gets the three entries.
- `go-build`'s manifest gains a `build` object (`main`, `targets`, `ldflags`, `cgo`, `flags`) so the provenance can state the build flags: a connector only sees its own config, not `[connectors.go-build]`. Additive; `go_build.py` was not in the task's file list.
- `release secret set` reads one line, so a PEM cannot be typed into it: `cosign-key` accepts the PEM (env var or keychain, real newlines or `\n`) **or its base64 on one line** (`base64 < cosign.key | tr -d '\n'`, 872 chars, under the terminal's line limit). Secret names are configurable (`key_secret`, `password_secret`); the password is required (a key with an empty password is not supported).
- `tlog = true` is refused (clear error) instead of implemented: nothing in the plan needs it and it cannot be tested offline. cosign **3.x** is required (the `--signing-config` flag); older cosign fails with its own "unknown flag".
- `sign` verifies its own output with the public key before reporting ok, so a public key that is not the key's pair fails the step; the attestation is checked against an archive (the statement's subjects), never against `checksums.txt`.
- The go fixture is unchanged: tests generate key pairs per run, so no key material is in the repo (the roadmap's "committed `cosign.pub`" is the user's app repo).
- `install.sh` is not covered by the signature or the provenance (it is not in `checksums.txt`; same as phase 2).
- While probing cosign before writing the config I ran one default `sign-blob` with a throwaway key on a file containing "hello": it created one public Rekor entry (a hash and a throwaway public key, nothing about the maintainer or this repo). Nothing in the code or tests can upload.
- Not run: a real run in a hosted/local CI with the user's actual key; `release secret set cosign-key` with the 872-char paste in a real TTY.
