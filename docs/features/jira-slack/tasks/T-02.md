# T-02: secrets store and `release secret`

- **Roadmap:** ../ROADMAP.md · **Phase:** 1 · **Repo:** release-cli · **Base branch:** release/jira-slack-p1 · **Branch:** feature/secrets
- **Depends on:** none · **Model:** sonnet

## Goal
Tokens and webhook URLs live in the OS keychain (or env), never in a TOML file, run state, or log line.

## Scope
- Files: new `release_cli/secrets.py`, subcommand in `release_cli/commands.py`, README section.
- Out of scope: the connectors that read secrets.

## Contract
Roadmap → Contracts → Secrets.

## Acceptance criteria (executable)
- [ ] `get` order env → keychain → secret-tool → None, with the keychain/secret-tool calls faked by a script on PATH — `pytest tests/test_secrets.py -q`
- [ ] `release secret set jira-token` reads with getpass (never argv, never echoed); `ls` shows names only; `rm` removes — same file
- [ ] A secret value never appears in stdout/stderr of those commands — same file
- [ ] `uvx ruff check .`; repo rules: test-suite-prune

## Result (filled by the worker)

- `release_cli/secrets.py`: `get(name)` env `RELEASE_SECRET_<NAME>` → `security find-generic-password` → `secret-tool lookup` → `None`; `set_`/`rm`/`names`. `release secret set|rm|ls` in `commands.py`, README "Secrets" section, help epilog line.
- Criteria, all run here:
  - `get` order with fakes on PATH — `uv run --with pytest pytest -q tests/test_secrets.py`: 10 passed (`tests/test_cli.py` too, 23 passed).
  - `set` reads with getpass; the fake logs every argv and the value is not in it; `ls` prints names only; `rm` removes (and a second `rm` exits 1) — same file.
  - Value absent from stdout/stderr of set, ls, rm and the "no keychain" error — same file.
  - `uvx ruff check .` — all checks passed.
- Decisions the contract left open:
  - `set` on macOS runs `security -i` and sends `add-generic-password … -X <hex>` on stdin, so the value is on no command line (`ps`). Checked by hand on a throwaway keychain (never the user's): ASCII values with spaces, quotes and backslashes read back identical; a non-ASCII value reads back as hex, so `set` refuses non-ASCII/control characters.
  - Neither keychain can list items by service, so `ls` reads a names-only index `~/.config/release/secrets.index` (written by `set`, trimmed by `rm`) plus the names of any `RELEASE_SECRET_*` env vars. It never holds a value.
  - Names are `[a-z0-9][a-z0-9-]{0,63}`.
  - `set` stores in macOS Keychain if `security` is on PATH, else `secret-tool`, else fails pointing at the env var.
- Not run: the full suite (CI does), and `secret-tool` against a real keyring (fake only).
