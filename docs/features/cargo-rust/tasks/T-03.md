# T-03: Shared packaging: zip, bare binary, `sign` covers binaries

- **Roadmap:** ../ROADMAP.md · **Phase:** 1 · **Repo:** release-cli · **Base branch:** release/cargo-rust-p1 (PR targets it, not main) · **Branch:** refactor/shared-packaging
- **Depends on:** none · **Model:** sonnet · **Review tier:** read (provenance subjects and signature checks)

## Goal
Any builder connector (go-build today, cargo-build in T-04) produces the same layout with one shared module, can ship
reproducible `.zip` archives and a bare Windows `.exe`, and `sign` verifies and attests that exe like an archive.
Go releases come out byte-identical to today's.

## Scope
- New `release_cli/packaging.py` with what `go_build.py` holds privately today: `_sha256`, reproducible tar.gz
  (`_add`, `_archive`), the worktree checkout at the tag (`_build`'s `git worktree add/remove/prune`), the `dist/`
  git-ignore guard and output-folder swap from `run`, `checksums.txt` + `manifest.json` writing and the
  "nothing reaches the output folder until every target built" rule from `_package`. Public names, docstrings.
- New in it: a reproducible zip writer (sorted entries, fixed `date_time` 1980-01-01, fixed `external_attr`
  (0o755 for the exe, 0o644 for the rest), `ZIP_DEFLATED`), and support for `kind: binary` entries (with `os`,
  `arch`) in checksums and manifest.
- `go_build.py` uses the module; its behaviour and output do not change.
- `sign.py`: `statement` subjects, `_check_on_disk` and line 333's subject list include `kind: binary`; the
  attestation sample stays an archive; messages "run go-build again" / "the go-build manifest" become builder-neutral
  ("run the build connector again"). `homebrew_tap.py`: confirm it ignores `.zip` / `binary` entries (Windows
  isn't a formula target); change it only if it doesn't.
- README: the layout table gains the `.zip` and `binary` rows.
- Out of scope: cargo anything (T-02, T-04), `github-release` (it already uploads every non-npm entry; confirm with a
  test, don't change it).

## Contract
Roadmap → Contracts → Layout and manifest (zip and exe names, `kind: binary`, `checksums.txt` lists archives and
binaries).
- **Non-functional:** go-build output byte-identical for the same commit (same checksums); provenance for an existing
  go release unchanged (no `binary` entries there).

## Decision (don't reopen)
- **Chosen:** extract and share — two builders must not drift on the layout `sign`, `github-release` and
  `homebrew-tap` rely on.
- **Rejected:** copying the helpers into `cargo_build.py`; a generic "builder base class". Plain functions.
- **Explicitly out of scope:** Authenticode signing; bare binaries for non-Windows targets.

### Decisions not in the spec
- **The layout table is in `docs/connectors.md`, not `README.md`.** The README has no layout table (the layout is prose under `go-build` in `docs/connectors.md`), so the rows went into a new table there. The `sign` paragraph there now says "archive and bare binary".
- **`write_zip` details the spec left open:** `compresslevel=9`, `create_system=3` (unix) so Windows and macOS hosts write the same bytes, `external_attr = (0o100000 | mode) << 16` (regular file + the given permission bits).
- **`packaging.finish` returns the manifest and takes `extras`** for entries that follow `checksums.txt` (go-build's `install.sh`), which keeps go's manifest order unchanged. `BuildError` lives in `packaging`; `go_build.BuildError` is the same class.
- **`sign` attestation sample:** still the first `archive`; falls back to the first subject only when a manifest has binaries and no archive (avoids a `StopIteration`).
- **`sign` messages made builder-neutral only where the spec said** (the "run go-build again", "changed since go-build" and "the go-build manifest lists no archive" ones). The messages about `prior["go-build"]` (not run / not ok / output folder) stay, because they are true while that is the only key looked up (see below).
- **`homebrew_tap.py` not changed:** confirmed by `test_the_formula_ignores_the_windows_zip_and_the_bare_exe` that a Windows `.zip` and a `binary` entry do not change the formula.

### Assumptions
- A `binary` entry always carries `os` and `arch` (`packaging.entry` writes them only when both are given).
- `checksums.txt` keeps the one `<sha256>  <name>` line per file, sorted by name, as before.

### Not verified
- **Gap for T-04 (needs a decision before it starts): the consumers only read the `go-build` key of `prior`.** `sign._manifest`, `github_release` (line ~114), `homebrew_tap` (~107) and `npm_publish` (~231) all look up `prior["go-build"]`. A `cargo-build` result would be ignored by `github-release` (no assets uploaded) and refused by `sign`. This task's spec says not to change `github-release`, so I left all four alone. T-04's criterion "`sign` + `github-release` unchanged" will not hold until the lookup is made builder-neutral (a small shared helper, or `cargo-build` registers under that key). `sign`'s `buildType` also still ends in `/go-build/v1`.
- Zip bytes depend on the host's zlib at level 9; reproducible on one machine and across runs, not proven across zlib versions (same caveat the gzip archives already have).
- No Windows machine: the zip and exe were checked as files, not run.
