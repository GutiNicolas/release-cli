# T-03: built-in `jira` connector

- **Roadmap:** ../ROADMAP.md · **Phase:** 1 · **Repo:** release-cli · **Base branch:** release/jira-slack-p1 · **Branch:** feature/jira-connector
- **Depends on:** T-01, T-02 integrated · **Model:** sonnet

## Goal
`release connector add jira`: on a final, before the deploy, Jira ends up with the version `{artifact}-{X.Y.Z}`
released and the reviewed tickets delivered with it, so the platform allows the prd deploy. On an RC it only warns.

## Scope
- Files: new `release_cli/jira_connector.py` (protocol like `cursor_review.py`), `BUILTINS` in `connectors.py`,
  commit-range helper shared with `github_release.py` (extract, don't duplicate), README section (incl. the required
  order: `jira` before the deploy connector).
- Out of scope: Jira Data Center; transitions other than to the delivered status.

## Contract
Roadmap → Decisions and Contracts (`multi`, secrets, config keys, `jira` result). Jira Cloud REST v3, stdlib `urllib`:
issue (`fields=summary,status,fixVersions`), transitions (GET/POST), project versions (`GET /rest/api/3/project/{key}/versions`,
`POST /rest/api/3/version`, `PUT /rest/api/3/version/{id}` with `released: true`), issue update (`fixVersions` add).

## Behaviour
- `questions`: keys from the commit range (regex `[A-Z][A-Z0-9_]+-\d+`; final: since the previous final); summary and
  status in the label; `multi` with the project's keys ticked, other projects' keys unticked. First time in a project:
  `project_key` (text, persist; default the `jira_project_key` already stored for the deploy connector if the CLI
  passes it, else none) and `delivered_transition` as `choice` from the transitions Jira offers toward a status
  (default the one leading to "Delivered" when present; persist). Not configured (`[jira]` or token missing) →
  `applies: false` with how to set it.
- `run`, RC: no writes; result lists tickets not in `qa_statuses` as `warned`; always `ok`.
- `run`, final: zero tickets → fail. Create the version if missing (name exact, never rename an existing one); add it
  as fixVersion; transition each ticket not yet delivered; if all delivered, release the version (already released → ok).
  Any ticket failing → `ok: false` with the list and the resume command; the version stays unreleased. Idempotent on resume.

## Acceptance criteria (executable)
- [x] Against a fake Jira (local `http.server` in the test): final creates/assigns/delivers/releases in that order; a ticket that cannot be delivered fails and leaves the version unreleased; zero tickets fails; resume after fixing completes; RC writes nothing and warns — `pytest tests/test_jira_connector.py -q`
- [x] The token is never in the request config, run state, or output — same file
- [x] `uvx ruff check .`; repo rules: test-suite-prune
- [ ] Manual check documented in the PR: one real final on a test project, then the platform accepts the prd deploy

## Result (filled by the worker)

- Built `release_cli/jira_connector.py` (protocol 1, stdlib `urllib`), registered in `BUILTINS`; `release connector add jira` defaults `break_on_error` to yes. `github_release.py` now exposes `commit_range` and `git_log`, used by `release notes` and by the connector (one range definition).
- Criteria: `uv run --with pytest pytest -q tests/test_jira_connector.py tests/test_github_release.py tests/test_commands.py tests/test_connectors_contract.py tests/test_cli.py` passes (8 new tests against a local fake Jira: order create → assign → deliver → release, undeliverable ticket + resume, zero tickets, RC writes nothing, token never in output even when Jira echoes the Authorization header, not configured, questions from the commit range, first-time questions); `uvx ruff check .` clean.
- Manual check on a real project: **not run** (needs a real Jira). Steps are in the PR description.
- Decisions the spec left open:
  - The CLI does not pass the deploy connector's `jira_project_key` into this connector's `config`, so `project_key` has no default unless `config.jira_project_key` is present (then it is the default). The `issues` default is computed with `default_when` on the answered `project_key`.
  - The delivered *status* is not stored (only the transition name, per the Contracts). A ticket counts as `already` when its status equals the `to` status of that transition as offered on another ticket, or the transition name itself (usual: both "Delivered"). A ticket that is not there and is not offered the transition fails with that reason.
  - Questions list only the transitions offered from up to 5 sample tickets of the project, so a workflow state nobody is in is not offered; `delivered_transition` becomes free text when Jira offers none.
  - `base_url` must be https (http only for localhost, used by the tests).
  - Jira auth/network errors at question time block a final (recorded failed) and only skip on an RC.
- Release review (#15) changed: not configured now **blocks a final** at question time (an RC still skips),
  replacing `applies: false` above; on a final the chain refuses to start when `jira` comes after the deploy
  connector; `connector add jira` defaults to just before the first deploy connector; redirects refused.
- Known limitation: when the transition is named unlike its status (`Deliver` → `Delivered`) and *every* selected
  ticket is already delivered (e.g. a resume after only the version release failed), no ticket teaches the delivered
  status and the final fails. Workaround: release the version in Jira by hand, then resume from the deploy.
