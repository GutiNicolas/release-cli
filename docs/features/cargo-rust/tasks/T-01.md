# T-01: Spike: Windows GUI exe cross-compiled on macOS (xwin, then mingw)

- **Roadmap:** ../ROADMAP.md · **Phase:** 1 · **Repo:** release-cli · **Base branch:** release/cargo-rust-p1 (PR targets it, not main) · **Branch:** spike/cargo-windows-cross
- **Depends on:** none · **Model:** sonnet · **Review tier:** evidence

## Goal
We know, with exact commands, whether a minimal eframe/egui (glow backend) app builds on macOS into a Windows `.exe`
that starts and shows its window, and with which toolchain. T-04 implements only what this proves.

## Scope
- Throwaway app in the scratchpad (not in the repo, not in `tests/fixtures`): `cargo new --bin acme-window`,
  edition 2024, `eframe` with `default-features = false, features = ["glow", "default_fonts"]`, one window with a
  label showing `env!("CARGO_PKG_VERSION")`, `#![windows_subsystem = "windows"]`, `Cargo.lock` committed in it.
- Committed deliverable: `docs/features/cargo-rust/spike-windows.md`: host (macOS version, arch), `rustc -V`,
  tool versions, every install command run, the build command per path, exe size, the result per path, and what
  T-04's toolchain checks must look for (binaries, env vars, licence step).
- Path A: `x86_64-pc-windows-msvc` with `cargo-xwin` (`cargo install --locked cargo-xwin`). Path B, only if A fails
  or the user asks: `x86_64-pc-windows-gnu` with mingw-w64 (`brew install mingw-w64`).
- `cargo` is not on PATH on this machine (rustup is installed). Set it up with rustup; say what you ran.
- Out of scope: any change under `release_cli/` or `tests/`.

## Contract
None (findings only). Record the facts T-04 needs: binaries that must be on PATH, the target names to `rustup target
add`, any env var or first-run download (xwin fetches the MSVC CRT and Windows SDK) and where it is cached.

## Decision (don't reopen)
- **Chosen:** msvc via cargo-xwin first — it's the standard Windows ABI and what a hosted Windows runner builds.
- **Rejected:** checking the exe under Wine on macOS. glow needs OpenGL, so a Wine run proves nothing. Don't use it as
  evidence.
- **Licence:** if xwin (or anything else) needs a licence accepted (Microsoft CRT/SDK), **stop and ask the user** to
  accept it themselves; never pass an accept flag or env var on their behalf. Record the exact step in the doc.
- **Explicitly out of scope:** code signing, icons, installers.

## Acceptance criteria (executable)
- [ ] Path A builds — `cargo xwin build --release --locked --target x86_64-pc-windows-msvc` exits 0 in the
      throwaway app; `file target/x86_64-pc-windows-msvc/release/acme-window.exe` says `PE32+ executable (GUI) x86-64`
- [ ] **Gate (user):** the user copies the exe to their Windows PC, double-clicks it, and confirms that the window
      opens showing the version and no console window appears. Hand them the exe path and these steps; record their
      answer verbatim in the Result. Without it, the task is `blocked`, not done.
- [ ] If A fails (build or the user's check): the same two criteria for path B with
      `cargo build --release --locked --target x86_64-pc-windows-gnu`. If both fail: Result says so, status blocked,
      and the doc lists what was tried.
- [ ] A second build of the same commit gives the same sha256, or the doc says it doesn't and why (`shasum -a 256`
      twice, after `cargo clean`)
- [ ] `docs/features/cargo-rust/spike-windows.md` exists with every item in Scope — `test -s docs/features/cargo-rust/spike-windows.md`
- [ ] Nothing else changed — `git diff origin/release/cargo-rust-p1 --name-only` lists only that doc and this task file
- [ ] Nothing private in the diff — `git diff origin/main --name-only | xargs grep -niEf <forbidden list from the brief>` finds nothing
